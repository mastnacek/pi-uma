## Principy memory (5 vět na balíček)

### 1. pi-memory
Paměť žije jako plain Markdown v `~/.pi/agent/memory/`: kurátorská MEMORY.md (dlouhodobá), denní append-only logy a SCRATCHPAD.md checklist. Před každým turnem se do system promptu injectují v prioritě: otevřené scratchpad itemy (2K), dnešní daily log (3K tail) a MEMORY.md (4K, middle-truncated). Šest core tools (write/forget/restore/read/scratchpad/status) funguje bez závislostí; `memory_forget` vytváří recovery záznam pro pozdější restore. Volitelný qmd engine přidává search ve třech režimech: keyword (BM25, ~30ms), semantic (vektory, ~2s) a deep (hybrid + reranking, ~10s) — embeddingy se udržují automaticky v pozadí. Bez qmd je search vypnutý, ale zbytek funguje plně.

### 2. memorix
Memorix je local-first sdílená paměť vázaná na Git projekt: SQLite je autoritativní store, k níž in-process Orama (malé projekty), persistent SQLite FTS5 keyword index a volitelný LanceDB sémantický shadow index — všechny rebuildovatelné. Vrstevnatý model: Observation Memory (fakta, fixy, pitfalls, session souhrny), managed long-term (episodic/semantic/procedural se source evidencemi), Git Memory (commity → searchable engineering fakta) a Reasoning Memory (důvody, alternativy, trade-offy). Memory Autopilot skládá pro novou session budgetovaný Workset: startovní soubory, aktuální vzpomínky, zdrojovou znalost, workflow kroky, rizika a validační návrhy. Knowledge Workspace drží claims s review gatingem — návrhy tiše nepřepíší reviewnuté stránky; stabilní znalost se promuje do reusable project skills. Všechny agenti (Claude Code, Codex, Cursor, Pi, OpenClaw...) se připojí přes MCP/hooks/rules/CLI na stejný lokální pool; `orchestrate` koordinuje paralelní agenty (handoffy, file locky, verifikační gaty).

### 3. gentle-engram
Engram je local-first „one brain" pro víc agentů: jediné Go binárko zapisuje do SQLite + FTS5, bez Node/Python služby nebo cloudu. Ukládá kurátorské souhrny, rozhodnutí, prompty a session handoffy místo raw tool-call dumpů — agent nejdřív hledá, pak fetchne jen relevantní vzpomínku (token-efficient). Memory Protocol před compactionem pushne souhrny do Engramu, takže další session recoverne, na čem záleželo. Local bridge ownership protocol na `pi.events` bus routuje session registrace a prompt capture (SHA-256 digesty, redakce privátních tagů, dedup per session/projekt). Volitelný Engram Cloud přidává opt-in projekt-scoped replikaci a dashboard, lokální SQLite zůstává autoritativní; přes MCP sdílí paměť Pi, Claude Code, OpenCode, Cursor aj.

### 4. pi-hermes-memory
Kombinuje persistent memory, full-text session search a secret scanning: všechny minulé konverzace se indexují do SQLite FTS5 (`/memory-index-sessions`) a Markdown vzpomínky se mirrorují do SQLite pro unified search. Tři typy znalosti: MEMORY.md (fakta, max 5K znaků), USER.md (profil, 5K) a Pi-native SKILL.md procedurální skills (neomezené, discoverable). Background learning každých 10 turnů (nebo 15 tool callů) reviewne průběh a uloží, co stojí za to; correction detection ukládá okamžitě, failure memory pamatuje, co nefungovalo a proč. Každý zápis (memory i skills) prochází security scannerem — API klíče, tokeny a SSH klíče se do persistence nedostanou. Auto-konsolidace merguje záznamy při naplnění kapacity (nikdy neztratí data), memory aging nese timestamps, dvoutier memory = global + per-project, extended store drží policy-only vzpomínky searchable i nad Markdown export cap.

### 5. pi-blackhole
Merge dvou projektů: deterministická kompaxe (pi-vcc) + observational memory. `/blackhole` nahrazuje LLM `/compact` algoritmickým structural souhrnem — compile() pipeline extrahuje strukturované sekce (goal, files, commits, preferences, brief transcript) bez modelového callu, tedy zero-cost. Observational memory běží přes tři background workery: Observer zachytává timestamped fakta, Reflector destiluje durable reflections, Dropper ředí — vše jako billed model cally s per-worker fallback chainy a persisted cooldowny, do session ledgeru přežívajícího kompaxe. Agent má unified `recall` tool: BM25 search nad raw session souborem (bypassuje kompaxi), expand záznamu #N s drill-downem do souborů/zpráv, recovery evidence podle ID. Config je jeden JSON (global → project → env → session); maintainer sám říká: experimentální, workerům dávej cheap/free modely, jinak stojí víc než nic.

### 6. om-memory-system (OMMS)
Po každém kusu práce background model call sumarizuje, co se udělalo a rozhodlo (fixy, design choices, co nefungovalo), do per-projektové paměti — automaticky, bez ptaní. Relevantní vzpomínky se přidávají do kontextu při každém promptu (OpenCode v2 a Pi), takže agent nestartuje od nuly. User profile s návyky uživatele se buduje v čase a následuje ho napříč projekty. Embedding model se stáhne při prvním použití (lokální, searchable vzpomínky), vše zůstává na stroji a Pi + OpenCode sdílí jednu paměť per projekt (Claude Code přes hooks plugin s vlastním API). Staré sessiony se importují po startu, lokální web UI ukazuje každou vzpomínku a profil; text v `<private>` tazích se nikdy neukládá.

### 7. @cortexkit/pi-magic-context
Pi/OMP varianta Magic Context enginu (viz GitHub #21), sdílející SQLite databázi s OpenCode pluginem — vzpomínky psané v jednom harnessu se objeví v druhém. Každá zpráva se tagguje `§N§` pro pozdější selektivní drop přes `ctx_reduce`; Historian background subagent komprimuje starou konverzaci do compartments + facts při threshold pressure nebo commit boundaries. `<session-history>` injection prependuje komprimovanou historii do system promptu každý turn, takže agent neztrácí kontext. Project memories jsou persistent cross-session store s embedding-based semantic search a Dreamer subagent je pravidelně konsoliduje, verifikuje, archivuje a vylepšuje. Auto-search hint připojí kompaktní memory nápovědu, když prompt zmiňuje dříve probíraná témata; note nudges surfacují odložené záměry na pracovních hranicích (commit, dokončený todo, historian publikace).

### 8. pi-observational-memory
Princip observational memory: místo opakovaných LLM sumarizačních řetězců (kompaxe kompaxe kompaxe...) se paměť zachytává průběžně během práce. Dva koncepty: Observations (konkrétní události — rozhodnutí, dokončená migrace, lokalizovaný bug, deadline) a Reflections (trvanlivé fakty destilované z observations — stack projektu, constrainty, preference). Reflector hodnotí coverage každé observation (none/partial/strong) jako review kontext a durable reflection nese support ids přesně těch observations, jejichž význam zachovává — ty pak slouží dropperu jako coverage evidence pro ředění. Když přijde kompaxe, paměťová práce je už hotová, takže proběhne rychle a sotva si jí všimnete. V3 model; cíl je praktická kontinuita přes týdny práce, ne „nekonečná paměť".

### 9. @llblab/pi-state-flow
Inkrementální state/memory kompilátor inspirovaný explicit-state přístupem SKILL.state: místo nosení celé dokončené konverzace do dalšího requestu agent postupně kompiluje requirements, rozhodnutí, nálezy a zdrojovou znalost do trvanlivého stavu. Stav má tři ownership scopy (global → cwd → session), které se rekurzivně komponují do effective view, a sémantické planes: intents, contract (požadavky/rozhodnutí/zamítnuté cesty), working, artifacts, response a lazy (mimo baseline kontext, čitelný explicitně). Agent updatuje stav atomickými `patch_state` cally (merge rekurzivně, null maže klíč, inference barrier během active epizody) a čte přes `read_state` s historií (historyLimit default 7 transitions). Další run dostane accepted state + kompaktní recent transitions místo historie, takže prompt cache prefix zůstává byte-stable a netřeba opakované LLM sumarizace. Persistence je JSON checkpoint + patches.jsonl per scope, volitelné git backupy; módy Active/Passive/Off; native kompaxe i append-only Pi trace zůstávají netknuté.

### 10. @remnic/plugin-pi
Remnic je local-first store, kde každá vzpomínka je plain Markdown soubor s YAML frontmatter na disku — žádná databáze, cloud ani subscription, cat/grep/git nad pamětí. Jeden store sdílí všechny nástroje (OpenClaw, Claude Code, Codex, Cursor, Pi, omp, MCP klienti): preferenci řeknete jednomu agentovi, znají ji všichni. Automaticky sleduje konverzace, destiluje durable knowledge a injectuje správný kontext zpět, když je potřeba. Retrieval je hybridní — BM25 + vektory + reranking nad rebuildable indexy, s graph recallem, memory-worth skóringem a per-result provenance k inspekci. Nad tím stojí i produkty jako „What Helps Me" (soukromý support passport: owner vybírá vzpomínky, model draftuje karty, owner schvaluje, sdílení exact verzí na čas, okamžité odvolání — model je scribe, člověk autor).

### 11. openlore
OpenLore není konverzační paměť, ale architektonická: jednorázová statická analýza repa staví živý knowledge graph (call struktura, typy, testy, rozhodnutí, IaC, spec drift) — deterministicky, local-first, žádný LLM v hot path, stejná odpověď pokaždé. `orient(task)` vrátí v jednom callu (~430µs p50) relevantní funkce, jejich callery, matching specs, testy a insertion points, takže task začíná orientovaný místo tuctu exploratory readů (−26% round-tripů). Anchored notes a rozhodnutí přežijí refaktoring (přenášejí se při rename/move symbolu) a agent je varován, když fakt zestárne. Governance polovina: `certify_public_surface` klasifikuje změny exportů breaking/non-breaking a jmenuje zasažené consumery, `change_impact_certificate` flaguje nové cesty do deklarovaných boundaries, `verify_claim` potvrzuje/vyvrací tvrzení s citací, `openlore enforce` je commit gate. Kód, IaC (21 jazyků + 12 ekosystémů) i architektonická rozhodnutí žijí na jednom grafu.

### 12. @pi-unipi/memory
Memory balíček unipi workstation suity: SQLite + vector search ukládá fakta, preference a rozhodnutí, project-scoped i global, takže agent pamatuje, co jste mu řekli minulý týden. Agent tools `memory_store` / `memory_search` / `memory_delete` dělají CRUD; commands `/unipi:memory-process|search|consolidate|forget` řídí zpracování, konsolidaci a zapomínání. Sedí vedle Compactor enginu (zero-LLM 6-stage pipeline, 95%+ token redukce, session continuity a session recall), takže krátkodobá kontinuita i dlouhodobá paměť jsou oddělené vrstvy. Balíčky spolu komunikují přes event systém (MODULE_READY, subscribes), ne přímé importy — memory lze použít standalone. Prefix-cache architektura celé suity drží append-only request disciplínu pro cache hit rate.

### 13. @yandy0725/pi-memory
Souborová paměť zarovnaná s auto-memory mechanismem Claude Code: jedna vzpomínka = jeden Markdown soubor s pěti frontmatter poli (name, description, type, created, modified), uložené per-projekt v `~/.pi/memory/<git|local>/<projekt>/` — clone a worktree stejného repa sdílí paměť. `MEMORY.md` index (jedna řádka = jedna vzpomínka, em dash) se injectuje jako `memory_index` system prompt section **zmrazená po celou session** — pi diffuje sections, takže prefix cache providera drží a resume/fork přehrává nahranou hodnotu místo čtení disku. Auto-surfacing vybírá každý user turn lehkým side query (vidí jen description) až maxFiles relevantních entries do `<relevant_memories>`; auto-extrakce (opt-in) žene po každém turnu headless agenta nad strukturovaným renderem celého turnu. `/dream` je headless údržbový agent (Orient → Gather Signal → Consolidate → Prune & Index) bez raw file přístupu — jen 7 memory actions, celou dobu drží logický zámek a na vstupu udělá snapshot adresáře. Injektovaný obsah se sanitizuje (bidi/neviditelné znaky, escape `<` `>`), zámky jsou dvouúrovňové (logický + milisekundový cross-process bez auto-recovery) a každý zápis nechává rollback bod v `.backups/`.

### 14. @bunshin-cc/bunshin
Bunshin je firemní sdílená paměť: agenti (Codex, Claude Code, Pi) se učí jeden od druhého — SPEC.md/TESTING.md/SKILL.md sekce repa, pravidla jiných týmů a zkušenosti z dřívějších session dorazí agentovi, když jsou relevantní. Co se session naučí, nejdřív se ověří lokálně (lessons v `.bunshin/`), pak projde review (`bunshin review`) a teprve schválené se sdílí do workspace — návrhy se neaplikují tiše. Na konci session běží reflection (u Claude Code jako fork session, takže reuse prompt cache) a vytěží znalosti; `bunshin learn` zachytí znalost on-demand, `/learn` v pluginu. `bunshin recall "<dotaz>" --hypothetical "<scénář>"` testuje, co by agent věděl; `bunshin index` ukazuje, jak se docs repa dělí na sekce. Setup instaluje hooky (5 Codex / 6 + MCP server Claude Code / projekt extension pro Pi), klíč agenta je v owner-only souboru mimo projekt; vše nad workspace účtem firmy, bez separátního model API klíče.

### 15. @amaster.ai/pi-memory-mem0
Extenze z amaster monorepa napojující Pi na mem0 (viz GitHub #1): sémantická paměť s automatickým capture, sémantickým recallem a agent-curated obsahem. Princip dědí mem0 pipeline: fakty se extrahují z konverzací (ADD-only), embeddují a ukládají, retrieval kombinuje semantic/keyword/entity signály. Agenty tak dostávají persistent, scoped vzpomínky napříč sessionami bez lokální údržby indexů. Registruje se standardně přes `./extension` subpath entry point do Pi runtime. Běží proti mem0 API (cloud nebo self-host), takže paměť je sdílená i mimo Pi.

### 16. @pify/memory
Dvoutier Markdown paměť (global `~/.pi/agent/memory/` + project `.pi/memory/MEMORY.md`) s denními logy podle lokálního kalendáře; design constraint: nikdy black box — agent píše jen na vyžádání nebo při korekci, žádný překvapivý model call při shutdown. Nedávné failure/correction lekce se recallují samovolně na startu session (newest first, max 8, 30 dní) — „lekce, kterou musíš hledat, se bude opakovat"; ostatní kategorie zůstávají jen searchable. Injekce přichází jednou za session jako hidden message před prvním promptem (ne system prompt → cache-stable prefix) a po kompaxi se re-attachuje model-free — změřeno: bez re-injekce paměť v 0/3 requestech po kompaxi, s ní 3/3. Každý zápis prochází secret gate (AWS/GitHub/Slack/Stripe/JWT… plus hodnoty secret-shaped env varů session), projekt paměť repa vyžaduje explicitní consent (repozitář nesmí „promluvit první"). Search je BM25 přes SQLite FTS5 (`node:sqlite`, zero deps), forget je undoable přes recovery záznamy, consolidation jen navrhuje (refuse při >60% ztrátě) a `/memory skill` promuje lekce do pi SKILL.md.

### 17. @amaster.ai/pi-memory
Persistent kurátorská paměť ze třídy MEMORY.md + USER.md: oba soubory se injectují do system promptu jako snapshot zmrazený mezi kompaxemi. Zmrazení drží prefix cache — system prompt je mezi kompaxemi byte-identický. Kurátorství znamená, že obsah je udržovaný (agent/flow rozhoduje, co patří do MEMORY.md vs USER.md), ne surový log. Extenze se registruje přes `./extension` subpath do Pi runtime, persistence přes `@amaster.ai/pi-storage` adaptéry (JSON soubory nebo MySQL/Prisma). Je součástí většího amaster ekosystému (sessions, artifacts, scheduled tasks sdílejí stejné storage kontrakty).

### 18. @josephyoung/pi-openviking
Owner-bound OpenViking (viz GitHub #2) extenze s tvrdým governance: explicit saves akceptují pouze verbatim span aktuální user zprávy — model-generated rewrite jména nebo čísla je blokován před enqueue. Recall je bounded a quoted, v non-persisted custom context message s host tokenizerem a per-request cache; consent je default-off a pause maže pending operace bez replay. Každý save má dedikovanou remote Session s persistovanými causal fázemi; neznámý message/commit outcome se reconciluje přes public APIs a nikdy se slepě nezretransmituje. Korekce/zapomínání stage-uje durable kopii nezávisle klasifikovaných nesouvisejících dokumentů před smazáním sdíleného zdroje; governance odmítne výběr, který by nechal fakt v remainderu dokumentu. Linux worker běží pod distinct UID s no_new_privs, immutable account/user bindingem, OS advisory locks a fsync — stav neslouží jako druhá memory databáze; „ready" vyžaduje retrieval probe scoped na changed owner-validated dokumenty.

### 19. open-zk-kb
Zettelkasten princip: atomické, linkované poznámky se strukturovanými kinds (rozhodnutí, preference, gotcha) — jedna poznámka = jeden koncept, odkazy staví propojený knowledge graf. Dual storage: Markdown soubory jsou source of truth, SQLite FTS5 + lokální vektorové embeddingy (MiniLM-L6-v2) jsou rebuildable index pro hybridní search. Pi extenze exposuje všech 10 `knowledge-*` tools nativně a na startu session automaticky naloží aktivní projektové preference do kontextu bez model-iniciovaného searchu. Běží lokálně offline bez API klíčů (vyžaduje Bun pro MCP server/SQLite/embedding práci), jeden vault sdílí OpenCode, Claude Code, Cursor, Windsurf, Zed, Pi i OMP. Note lifecycle má kinds, statuses a review systém; telemetrie je opt-in (PostHog EU, jen counts, nikdy obsah poznámek).

### 20. common-memory-core
User-owned Markdown long-term paměť sdílená mezi asistenty (Pi extenze, Codex read-only MCP, ChatGPT Desktop Work, stdio MCP hosty) — asistenti čtou podle autorizace, vlastníkem dat je uživatel. Když je potřeba paměť aktualizovat, nakonfigurovaný model **navrhne** maintenance rozhodnutí a lokální program ho zvaliduje a zapíše — model píše jen přes schválené návrhy. API Key se konfiguruje jen v TUI do privátního `.env`; stejnojmenné env var v terminálu/asistentovi ho nepřepíše. Core běží jako OS-supervised nezávislá služba: zavření Pi/MCP/TUI neruší accepted tasks, upgrade/repair se dokazuje instancí, unknown ≠ updated. Codex session capture odmítne neznámý formát místo hádání obsahu; instalace ověří read-only MCP bez model callů a bez zápisu do paměti.

### 21. @henryqw/pi-memory
Bounded Markdown paměť (MEMORY.md 8800 + USER.md 5500 znaků, entries oddělené `§`) inspirovaná Hermes Agent vzorem; na startu session se oba stor snapshotnou a zmrazí — pozdější edity nemění injektovanou paměť, prefix cache drží. Každý add prochází nezávislým review modelem (`pi-memory/reviewCandidate` Model Task přes `/task-models`, nikdy session model), který vidí live snapshoty SYSTEM.md/MEMORY.md/USER.md; přesné duplicity jsou idempotentní bez review. Konflikty (overlap/kontradikce) se během aktivní odpovědi queueují a po `agent_settled` se drénují FIFO přes ask_question UI: Merge / Discard / Replace s doporučeným pořadím — nic se nezapíše bez rozhodnutí, SYSTEM konflikt vyžaduje člověka. `/remember` použije bounded `prepareCandidate` task, který navrhne cíl a přesnou entry nebo odmítne (projekt-specifické/triviální obsahy se refuse); `/dream` promuje invariantní entries do agent-global `~/.pi/agent/SYSTEM.md` po preview schválení, SYSTEM se zapíše dřív než se entries smažou. Zápisy přes store lock s backupy mimo directory; proven-gone store blokuje zápisy do obnovy; per-turn pravidla: habits jen po dvou nezávislých signálech, projektová fakta patří do repa, ne sem.

### 22. @reddb-io/red-skills-memory

### 24. pi-knowledge

### 29. @arihantdeva/heimdall
Cross-repo „verified knowledge layer": Heimdall indexuje všechno, čeho se dotknete (všechny repa, poznámky, i emaily), do jednoho sémantického grafu — paměť není per-projekt, ale machine-wide.
